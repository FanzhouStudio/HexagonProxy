# HexagonProxy 与成熟代理客户端对比

评估日期：2026-09-07。依据本项目源码、自动化测试和对方官方文档；没有做相同节点、相同设备下的吞吐、内存或长时间稳定性对照实验。“Clash”按目前仍维护的 Clash Verge Rev 客户端比较，“v2nay”按 v2rayN 理解。

## 定位与结论

HexagonProxy 适合 Windows 浏览器代理、本地开发与 Codex 多账号使用。它的差异化在像素界面、桌面宠物、内置终端与账号额度管理。与成熟客户端相比，主要差距在网络接管、故障诊断和配置工具，而不是需要重新实现代理协议。

| 维度 | HexagonProxy 当前实现 | Clash Verge Rev | v2rayN |
| --- | --- | --- | --- |
| 内核 | Mihomo，支持常见分享链接本地转换 | Mihomo，提供内核版本选择 | 支持 Xray、sing-box 等多种内核 |
| 网络接管 | Windows 系统代理；未提供 TUN 开关和生命周期管理 | 系统代理、守卫、TUN | 系统代理及 TUN，具体行为依核心与配置而定 |
| 配置工具 | 多订阅、节点选择、按应用分流、指定备选节点故障切换 | 配置合并与脚本增强、节点和规则编辑、WebDAV 同步 | 自定义配置、路由与多核心管理 |
| 使用重点 | 像素界面、桌宠、终端、Codex 登录备份与额度 | Clash 配置管理与跨平台代理体验 | 多核心与自定义连接配置 |
| 平台 | 当前面向 Windows | Windows、macOS、Linux | Windows、macOS、Linux |

对方功能依据：[Clash Verge Rev 官方 README](https://github.com/clash-verge-rev/clash-verge-rev)、[v2rayN 官方 README](https://github.com/2dust/v2rayN)、[v2rayN 界面说明](https://github.com/2dust/v2rayN/wiki/Description-of-some-ui)、[维护者的 TUN 说明](https://github.com/2dust/v2rayN/issues/8977)。这些文档支持功能比较，不代表任何客户端永远不会断网。

## 已有优势

- 协议由独立 Mihomo 处理，UI、协调器和服务分层，便于在不改动协议实现的情况下迭代体验。参见 `scripts/app`、`scripts/modules/mihomo`。
- 多种分享链接在本地转换，局域网绕过、应用分流和指定备选节点的故障切换已有实现；故障切换包含阈值、冷却与熔断。参见 `scripts/modules/reliability/node_failover_service.gd`。
- Codex 账号备份、身份匹配、额度进度与恢复倒计时贴合个人开发场景。相比通用代理客户端，这是产品侧的差异化。
- 已有覆盖配置预检、节点切换、大订阅、UI 布局与账号事务的自动化检查。新发布流程统一文件名，成功导出后才覆盖旧包。

## 主要不足及实际影响

1. **系统代理不能覆盖所有应用。** 忽略 Windows 代理设置的程序不会因应用分流规则而自动进入 Mihomo；游戏和部分命令行工具尤其需要明确配置。应优先补齐 TUN 的启停、权限、路由恢复与 DNS 处理，而不只是添加一个开关。
2. **检测通过不等于目标业务可用。** 新增的双站点 HTTPS 探测能验证 mixed-port，但只证明这两个 URL 在当前规则下可达；它们可能走直连，无法证明某个指定代理节点、UDP、目标网站、登录流程或浏览器自带 DNS 都正常。下一步应记录目标域名、规则命中、出口节点、DNS/TLS 错误，并支持用户指定业务探测地址。
3. **系统代理恢复覆盖有限。** 当前核对 ProxyEnable 与 ProxyServer，尚未完整检测 PAC、浏览器扩展代理、其他代理软件冲突；不能把注册表修复成功等同于浏览器网络配置正确。参见 `scripts/windows_proxy_helper.ps1`。
4. **UI 和后台任务的隔离还需改进。** 额度自动查询目前会进入页面 busy 状态，导致与查询无关的按钮暂时不可操作；用户此前遇到的拉伸也说明需要覆盖不同 DPI、窗口宽度与长文本。下一步将查询状态限制在对应账号卡片。
5. **部署和资源优势尚未证实。** 当前便携 EXE 约 106 MiB，未内置 Mihomo；不能仅凭 Godot 或“轻量”定位宣称比成熟客户端更省内存、更快。需要测空闲 CPU/GPU、内存、启动时间及长时间运行。项目还需补充可验证的发布签名与更新回滚。
6. **登录凭据依赖本地文件保护。** Codex 登录备份不会上传到本项目服务器，但文件存储不等于加密存储。后续应评估 Windows 凭据保护、文件 ACL 和备份生命周期，并保持与 Codex 的凭据存储方式兼容。

## 建议优先级

1. 完善网络诊断：实际业务域名探测、路由与 DNS 可观测性、睡眠唤醒/切网/上游断线测试。
2. 增加可恢复的 TUN 模式，验证权限失败、应用崩溃、退出和网络切换后的路由清理。
3. 解决后台查询锁整页和不同 DPI 布局问题。
4. 再扩展高级配置编辑、同步、签名发布与更新回滚。

当前更合理的方向是先把 Windows 日常连接做可靠，再围绕 Codex 与开发工具保持特色。是否加入多核心应由具体协议兼容需求决定；增加核心也会扩大配置转换和测试成本。
